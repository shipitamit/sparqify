# Security

## Threat model

Sparqify reads **untrusted text** (SQL, pandas/R/SAS scripts, ETL exports such as XML/JSON, Excel formulas) and writes **Python/SQL source**
that someone may later run on a cluster. The main risks are:

1. **Injection into generated code**: a value in the input (a name, a path, a comment) breaks out of a string or comment and becomes code.
2. **Hostile files**: XML entity expansion / external entities, huge inputs, deeply nested expressions, symlinks in a project folder.
3. **The web UI**: other web pages calling your local server (CSRF, DNS rebinding), XSS, unbounded work.
4. **Data leaving the machine**: optional AI suggestions send code to an API; a CI comment is rendered as Markdown for others.
5. **`verify`**, which executes code by design.

## What is protected

| Area | Control |
|---|---|
| Converters never execute the input | Parsing only (`ast`, tokenizers, XML parser). Nothing is `eval`ed or `exec`ed. |
| Generated code | Untrusted text is quoted with `repr`/`cm()`/`dq()`/`tq()` helpers. For non-Python inputs `guard_output()` then parses the result and refuses it (`UnsafeOutput`) if it imports outside an allow-list or uses `eval/exec/open/os/subprocess/__import__`, dunder attributes, etc. |
| XML | `safe_fromstring()` rejects DOCTYPE/ENTITY declarations and inputs over 50 MB. |
| Errors | Internal failures become `ConvertError` (CLI exits 2; web returns 400 with no traceback). |
| Projects | Symbolic links are not followed; files over 20 MB are skipped; output names are derived, never taken from the input. |
| Web server | Binds to loopback; refuses other addresses without `--token`; Host allow-list; same-origin check (Origin / Sec-Fetch-Site); JSON content-type required; CSP with per-response nonce, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, COOP/CORP; request size and concurrency limits; each conversion runs in a separate process with a 60 s timeout and memory/CPU limits. |
| AI suggestions | Off unless requested. https only (http for localhost). The provider comes from a fixed list; the web UI never takes a base URL from a request (only the server's own `SPARQIFY_AI_BASE_URL`), so a page cannot make the server call arbitrary hosts. Redirects are refused so the key is never forwarded. The key is scrubbed from error messages. Prompts are passed through `redact()` (passwords, tokens, AWS/GitHub/`sk-` style API keys, private keys, JWTs, `user:pass@` URLs). Suggested lines are stripped of control/line-break characters and, when applied live, must parse and pass the same AST checks; otherwise they stay comments. |
| CI comment | File names and messages are escaped: no HTML, links, images, `@mentions`, issue references; code spans cannot be broken out of. |
| Denial of service | Input capped at 20 MB (NUL bytes rejected); line-anchored regexes use `[ \t]*` instead of `\s*` and ambiguous nested quantifiers were removed (a 20,000-blank-line file took 30 s to classify before, 0.01 s now; probed with 16 hostile shapes across every example format); web requests are size-limited, concurrency-limited and time-limited; failed token attempts are throttled (10 per minute per client address, then HTTP 429). |
| Container / Kubernetes | Non-root UID, read-only root filesystem, all capabilities dropped, seccomp `RuntimeDefault`, no service-account token, NetworkPolicy (default deny; outbound HTTPS only if you add the optional AI egress policy), Pod Security `restricted`, token from a Secret and never written to logs, probes that touch no data. |
| Agentic mode (`sparqify agent`, web Assistant) | The model has no shell. It can only call tools that enforce the rules in code: project-folder-only reads (no symlinks, `..`, secret-looking names, size and total caps, redaction), edits to in-memory drafts refused unless they parse and add no unsafe construct, writes only to the output folder (extension allow-list, never over existing files, per-write approval by default), running code only in a no-network sandbox container and only if enabled, step/token/byte budgets. Prompt injection from file contents therefore cannot widen what the agent may do. The web assistant has no file or execution tools. |
| `verify` | Executes the script and its pandas twin. It refuses to run without `--trust` and is not available in the web UI. |

## What is *not* protected

- **The verify loop runs code, only in the sandbox.** `verify_draft` runs the original script and the draft inside the no-network container (never on the host); the original and the data are fixed by sparqify, the model can only patch the draft, and the report's verification table is generated by sparqify from the last real run. A match on sample data is not proof of equivalence.
- **Agent output is unverified** unless the verify loop ran and matched, and then only on your sample data. A prompt-injected or simply wrong model can still produce bad *logic* (a wrong filter, a changed join) inside the allowed constructs, and can mislead you in its summary. Review diffs and run `verify`. File contents you let the agent read, and the code the web assistant is given, are sent to the model provider you configured after pattern-based masking.
- The sandbox option shells out to Docker with a fixed argument list; it was not tested against a real daemon, and a container is not a perfect boundary: use a hardened runtime (gVisor, Kata) for hostile code.

- **Generated code is still code.** Review it before running, especially from inputs you do not trust. `guard_output` is a safety net, not a proof.
- Redaction is pattern-based; a secret in an unusual format can still reach the AI API. Use `--ai-dry-run` to see exactly what would be sent, or leave AI off for sensitive code.
- `verify --trust` runs arbitrary code with your permissions. Use a throw-away container for third-party scripts.
- The web server is meant for one local user or a small trusted team. If you expose it, put it behind TLS. To tell people apart use per-user tokens (`--users-file`, `sparqify users add`) or single sign-on at a reverse proxy (`--auth-header` together with `--proxy-secret` and `--trusted-proxies`). The identity then appears in the access log, and `--user-rpm` / `--ai-daily-limit` limit each person. Users files hold SHA-256 hashes of random tokens, never the tokens; the proxy-supplied name is only trusted when the request also carries the proxy secret.
- Resource limits rely on OS facilities (`resource`, process isolation) and are weaker on Windows.
- Expression parsers have recursion limits only through Python's own; extreme inputs end as `ConvertError`, not a crash.

## Deployment notes

- Behind a reverse proxy or ingress every request appears to come from the proxy's address unless you set `--trusted-proxies`; without it the brute-force throttle locks out *all* users for a minute after 10 bad attempts. Set it, rate-limit per client at the ingress as well, and keep tokens long and random.
- `.github/workflows/image.yml` builds the image, scans it with Trivy (fails on fixable HIGH/CRITICAL), checks it runs as non-root with a read-only filesystem and dropped capabilities, validates the manifests, and on a version tag pushes it with provenance + SBOM and signs it with cosign (keyless). Verify with `cosign verify` before deploying.
- Run `scripts/pin_actions.sh` once (needs `gh auth login`) to replace action version tags with commit SHAs; the tags in the repo are not pinned yet because they could not be resolved offline. Also pin the `FROM` images in the `Dockerfile` by digest.
- The app has no third-party Python dependencies, so the OS layer is the main thing to patch.
- Rotate the shared token by updating the Secret and restarting the Deployment. Per-user tokens: update the users Secret; the server re-reads the file when it changes (a bad file is ignored and the previous users stay valid). Remove a person by deleting their line.
- Behind a reverse proxy set `--trusted-proxies N` / `SPARQIFY_TRUSTED_PROXIES`: the failed-token throttle then keys on the client address from `X-Forwarded-For` (the Nth entry from the right, which a client cannot forge) and HSTS is sent for https. `--access-log` / `SPARQIFY_ACCESS_LOG=1` logs method, path without query, status, client and duration; never tokens or bodies. `/metrics` requires the token.
- Worker count and memory are set through `SPARQIFY_MAX_CONCURRENT` / `SPARQIFY_WORKER_MEMORY_MB`; keep the container memory limit above their product plus about 300 MB. The server handles SIGTERM (stops accepting, finishes running conversions for `SPARQIFY_DRAIN_SECONDS`).

## Deploying the GitHub Action safely

- Run it on `pull_request`, **not** `pull_request_target`, so that code from forks never runs with write tokens.
- Give the job only `contents: read` and `pull-requests: write`.
- Pin third-party actions to a commit SHA.
- The action never runs `verify`.

## Reporting a vulnerability

Open a private security advisory on the repository (or email the maintainer) with a minimal input that reproduces the problem.
